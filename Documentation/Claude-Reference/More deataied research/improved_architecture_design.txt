## Executive Summary

This document presents a comprehensive architectural redesign of the FileSorter

application, incorporating the proven token-limit-safe methodology from QiuYannnn/

Local-File-Organizer [1] while leveraging Apple's latest Foundation Models framework

and macOS 26 capabilities. The core innovation lies in adapting the per-file processing

approach that successfully sidesteps token limitations through isolated inference calls

and JSON-based metadata persistence.

The QiuYannnn project demonstrated that effective file organization at scale requires

breaking away from traditional batch processing approaches that overwhelm language

models with massive context windows. Instead, their architecture processes each file

individually, builds intermediate metadata files, and uses separate lightweight passes

for different modalities (text and image analysis). This methodology eliminates token

overflow issues while maintaining sophisticated AI-driven categorization capabilities.

Our improved FileSorter 2.0 architecture adapts these principles to Apple's ecosystem,

incorporating Foundation Models adapters, Vision framework capabilities, App Intents

integration, and the new macOS 26 design language. The result is a modern, scalable file

organization system that can handle large directories without token limitations while

providing native macOS integration and privacy-preserving on-device processing.


## Current Architecture Analysis

### Existing FileSorter Limitations

The current FileSorter implementation, while functional, suffers from several

architectural limitations that the QiuYannnn methodology directly addresses:

**Token Limit Vulnerability** : The existing OrganizationEngine.swift attempts to

process multiple files in batch operations, creating prompts that can easily exceed the

Foundation Models framework's token limits. The current approach builds file tree

summaries and processes loose files in groups, which becomes problematic with large

directories containing hundreds or thousands of files.

**Monolithic Processing** : The current architecture tries to analyze entire directory

structures in single LLM calls, as evidenced in the organizeDirectory method that

processes all loose files in a directory before moving to subdirectories. This approach

works for small file sets but fails catastrophically when encountering large collections.

**Limited Multimodal Support** : While the current FileAnalyzer.swift includes some

audio analysis capabilities, it lacks the sophisticated multimodal pipeline that

QiuYannnn demonstrated with separate text and image processing phases.

**Insufficient Metadata Persistence** : The current implementation doesn't maintain

intermediate metadata files, meaning that processing failures require complete restart

of the organization process rather than resuming from the last successful state.

### QiuYannnn's Breakthrough Methodology

The QiuYannnn/Local-File-Organizer project solved these fundamental problems

through a carefully designed architecture that processes files individually and maintains

persistent metadata throughout the organization process.

**Per-File Token Isolation** : Instead of batching files into giant prompts, the system

processes each file through individual inference calls. This approach ensures that no

single operation exceeds token limits, regardless of directory size or file complexity.

**JSON-Based Metadata Strategy** : The system builds intermediate .json metadata files

for each processed item, creating a persistent record of analysis results that can survive

process interruptions and enable incremental processing.

**Decoupled Multimodal Pipeline** : Text and image metadata extraction run as separate

lightweight passes, allowing token space optimization for each modality. This separation

enables specialized prompts for different file types without cross-contamination.


**Streaming Architecture** : The processing pipeline streams through files sequentially,

maintaining constant memory usage regardless of directory size and enabling real-time

progress reporting.

## Proposed FileSorter 2.0 Architecture

### Core Design Principles

Building on the QiuYannnn methodology, FileSorter 2.0 adopts the following

architectural principles:

**Principle 1: Per-File Processing Isolation**

Every file analysis operation occurs in isolation with its own dedicated LLM session. This

ensures predictable token usage and eliminates the possibility of context overflow

regardless of directory size or file complexity.

**Principle 2: Persistent Metadata Architecture**

All analysis results are immediately persisted to JSON metadata files, creating a

recoverable processing state that survives application crashes, system reboots, or user

interruptions.

**Principle 3: Multimodal Pipeline Separation**

Different file types (text documents, images, audio, video) are processed through

specialized pipelines optimized for their specific analysis requirements, preventing

token waste on irrelevant context.

**Principle 4: Incremental Processing Model**

The system supports resuming interrupted operations by checking for existing metadata

and only processing files that haven't been analyzed or have changed since last analysis.

**Principle 5: Apple Ecosystem Integration**

All processing leverages Apple's on-device capabilities including Foundation Models,

Vision framework, and App Intents while maintaining the token-safe methodology.

**3. Specialized File Type Analyzers**

Following QiuYannnn's multimodal approach, FileSorter 2.0 implements specialized

analyzers for different file types:

**Text File Analyzer** : Processes documents, PDFs, and text files using Foundation Models

with document-specific prompts. Extracts content summaries, identifies document

types, and suggests categorization based on semantic content.

**Image File Analyzer** : Leverages both Vision framework capabilities and Foundation

Models for comprehensive image analysis. Uses Vision for text recognition and object

detection, then applies Foundation Models for semantic categorization and content

description.

**Audio File Analyzer** : Analyzes audio files using AVFoundation for technical metadata

and Foundation Models for content-based categorization. Distinguishes between music,

voice recordings, sound effects, and other audio types.

**Video File Analyzer** : Combines video metadata extraction with frame sampling for

content analysis, using both Vision framework and Foundation Models for

comprehensive video understanding.

## Integration with Apple's Foundation Models

### Custom Adapter Training Strategy

FileSorter 2.0 leverages Apple's Foundation Models adapter training capabilities [2] to

create specialized file categorization models:

**File Type Specialization Adapter** : Trained on datasets of file categorization examples,

this adapter specializes the base Foundation Model for understanding file organization

patterns, naming conventions, and content-based categorization strategies.

**Domain-Specific Adapters** : Additional adapters can be trained for specific domains

(creative workflows, business documents, academic research) to provide specialized

categorization logic for different user contexts.

**Training Data Generation** : The per-file processing approach generates high-quality

training data by collecting user categorization decisions and file analysis results,

enabling continuous improvement of the categorization models.

## Performance and Scalability Considerations

### Memory Management

The per-file processing approach provides excellent memory management

characteristics:

**Constant Memory Usage** : Processing memory usage remains constant regardless of

directory size, as only one file is analyzed at a time.

**Metadata Streaming** : File metadata is streamed to disk immediately after analysis,

preventing memory accumulation during long-running operations.

**Lazy Loading** : File contents are loaded only when needed for analysis, minimizing

memory footprint for large directories.

### Processing Efficiency

The token-safe methodology provides predictable performance characteristics:

**Linear Scaling** : Processing time scales linearly with the number of files, providing

predictable completion estimates.

**Parallel Processing** : Multiple files can be processed in parallel while maintaining per-file

token isolation.

**Incremental Progress** : Users can see immediate progress as each file is processed,

rather than waiting for batch operations to complete.

### Error Recovery

The persistent metadata approach enables robust error recovery:


**Graceful Interruption** : Processing can be interrupted at any point and resumed from

the last completed file.

**Partial Results** : Successfully analyzed files retain their categorization even if later files

encounter errors.

**Retry Logic** : Failed analyses can be retried without reprocessing successful files.
